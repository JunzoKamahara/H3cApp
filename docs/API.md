# H3cApp local API reference

[English](API.md) | [日本語](API.ja.md)

This is a developer reference for scripting H3cApp locally. The app must be running. See the [README](../README.md) for installation.

## API

**The API is off until you turn it on** (from v0.10.0): in
**H3cApp > General Settings…** (⌥⌘,), API tab, turn on **Use the API**. It
starts listening at once, and the setting is kept for the next launch.
Turning it off closes the server and removes the token file; while it is
off no port is open and nothing is answered.

While `H3cApp.app` is running with the API on, it serves a plain JSON API on
`http://127.0.0.1:8420` — implemented over raw POSIX sockets (see
[HTTPServer.swift](../native/H3Spike/Sources/H3cApp/HTTPServer.swift)), not
Network.framework or any third-party server, and with no separate process
to start or stop. It drives the app's primary `GenerationViewModel`/engine
instance — the one the first window shows (see
[AppModels.swift](../native/H3Spike/Sources/H3cApp/AppModels.swift) and
[GenerationViewModel+API.swift](../native/H3Spike/Sources/H3cApp/GenerationViewModel+API.swift)).
It keeps answering with every window closed, as long as the app runs;
closing a window closes its project, so open one with
`POST /api/project/open` when needed. There is only ever one job at a time,
shared with the window showing that instance — pressing its generate button
and a `POST /api/generate` compete for the same slot, and whichever loses
gets a clear `409`.

POST requests from web pages on other origins get `403`: a request that
carries an `Origin` header other than `http://127.0.0.1:8420` or
`http://localhost:8420`, or `Sec-Fetch-Site: cross-site` / `same-site`, as a
browser adds, is refused, so a site you visit can't drive the app. Scripts
and `curl` send neither header and are unaffected; `GET` requests are
answered as before.

A request whose `Host` header names anything other than `localhost` or an
IP address (with any port) gets `403`, which keeps web pages out through DNS
rebinding: a page that points its own domain name at 127.0.0.1 still sends
that name as `Host`. curl and scripting libraries set `Host` from the URL, so
`http://127.0.0.1:8420`, `http://[::1]:8420` or `http://localhost:8420` just
works.

Every request must carry the app's API token as
`Authorization: Bearer <token>`; without it, or with a wrong one, every
endpoint, `GET` ones included, answers `401`. `127.0.0.1` can be reached by
every account and every process on the Mac, not only yours, and the API
reads your prompts, paths and results and writes files as you, so the token
is what keeps it yours. The app makes a new token each time it starts and
writes it to `~/Library/Application Support/H3cApp/api-token`, a file only
your account can read (mode `0600`), and deletes the file when it quits
normally; read the file each time a script starts rather than keeping a copy
of the token. **H3cApp > 全体設定…** (General Settings, ⌥⌘,) shows the
addresses and the token with buttons to copy them (and a curl example),
and **作り直す…** replaces the token at once. Do not put the token on a
command line or in a URL: other accounts on the Mac can read every process's command line with `ps`. With
curl, pass the header on standard input as in the examples below (`printf`
is built into the shell, so it never shows in `ps`); a script in another
language should read the file and set the header in its own code.

| Method | Path | Does |
|---|---|---|
| `POST` | `/api/generate` | Starts a job. JSON body fully replaces the current draft (see below); `202` once started, `400` on a bad request, `409` if a job is already running. |
| `GET` | `/api/status` | Engine/job state, progress fraction, phase/stage text, error message, and whether a result is ready. While several videos or a joined generation run, `batch` gives `index`/`total`/`chained` and the whole run's `elapsed_seconds` and `estimated_remaining_seconds` (the current video's live estimate plus the later ones, scaled by the pace seen so far); the top-level `estimated_remaining_seconds` stays the current video's. `generation_kind` is what the composer makes (`video` or `image`), `generating_image` whether the running generation makes images, and `form` the inputs the form holds: the video side's `prompt`, `creation_method`, `image_input_mode`, `first_frame`, `last_frame` and `references` (paths), and under `image` the image side's `prompt`, `size`, `width`, `height`, `count`, `references` (the pictures of an edit, as paths, in the prompt's order; empty for an image from the prompt alone) and `plan` (what the edit will take, once the form has worked it out - `null` until then and without references: `verdict` `ok` / `tight` / `too_large`, `text_tokens`, `vision_tokens`, `text_token_limit`, `dit_tokens`, `dit_reference_tokens`, `peak_bytes`, `memory_bytes`, `peak_stage`). |
| `POST` | `/api/cancel` | Cancels the running job, if any. |
| `GET` | `/api/result/video` | Streams the current result as `video/mp4`; `404` if none, or once the next job's `generate()` call deletes it. |
| `GET` | `/api/result/image` | The project image in the preview, as `image/png`; `404` when none is shown. |
| `GET` | `/api/models` | Registered H3 model directories (id, name, path, whether active). |
| `GET` | `/api/image-models` | Registered still-image model folders (id, name, path, whether active). An image model folder holds `transformer/` (the MiniMax H3 Image DiT), `vae/` (the image VAE and its `config.json`), `tokenizer/`; without a `text_encoder/` of its own (the same as a video model's), the `FL2VA/text_encoder` of a registered video model is read. `setup` describes the model the app downloads itself: `phase` (`idle`, `listing`, `downloading`, `copying the text encoder`, `verifying`, `done` or `failed: ...`), `location` (the folder the model's own folder is made in), `directory` (that folder), `installed`, `verified` (every weight's SHA-256 matched the pinned revision), `repo`, `revision`, `license`, `license_url`, `download_bytes`, while downloading `downloaded_bytes` / `total_bytes`, `text_encoder` (`own`: in the model's folder; `shared`: a video model's, read where it is; `needs_choice`: the chosen video model's was not found and those of the registered video models are not known to have the same contents (the same SHA-256 of each whole file), so none is read until it is chosen; `missing`: none to read), `text_encoder_directory` (the folder read, or `null`) and `text_encoder_video_model` (the folder of the video model chosen for it, recorded in the model's folder as `H3IMAGE_TEXT_ENCODER.json` with each file's size, the SHA-256 of its first MiB and the SHA-256 of the whole file; while it is not found, only another registered video model whose files are known to have the same whole-file SHA-256 is read; `null` when none was chosen). `phase` can also be `comparing the text encoder` (the check before a copy is given up) and `reading the text encoder` (a chosen video model's text encoder being read through for its SHA-256). |
| `POST` | `/api/image-models/add` | `{"path", "name"?}` registers an image model folder and makes it the active one; `400` with the reason when the folder is not one (a part is missing, or its transformer is a video model). Returns the list. |
| `POST` | `/api/image-models/setup` | `{"confirm_license": true}` starts the same chain as the setup sheet's button: downloads the MiniMax H3 Image DiT and VAE from Comfy-Org/MiniMax-H3-Image at its pinned revision (about 22 GB, resumable), fetches the VAE config, the tokenizer and the license text from MiniMaxAI/MiniMax-H3-Image, makes the text encoder of an installed video model available (a clone when the video model is on the same volume; on another volume no copy is made: the video model is recorded and its text encoder read where it is), checks every file's SHA-256 (a file that differs is deleted and named), writes the record beside the weights and registers the model. `400` without the confirmation - the MiniMax-H3-Image Community License Agreement applies, a different agreement from the video model's, which excludes the EU, the UK, the Republic of Korea and the USA for the model and for the images made; `409` while it is already running. A video model must be installed first. `"location"` (optional) is the folder the model's own folder is made in, on another disk for example - the sheet's Location; `null` goes back to the app's own. `400` with the reason when the model already has files at its present location (delete them in the sheet first), or when the folder is missing or cannot be written to. Returns the list; poll `GET /api/image-models` for `setup.phase`. |
| `POST` | `/api/image-models/setup/cancel` | Stops the setup (`409` if it is not running). A download resumes from where it stopped. |
| `POST` | `/api/image-models/share-text-encoder` | `{"video_model"?}` makes MiniMax H3 Image share a video model's text encoder (the setup sheet's 動画モデルと共用にする…): the copy in the model's folder and the text encoder of a registered video model holding the same files (names, sizes, first MiB) are read through in the background and their SHA-256 compared (`phase` is `comparing the text encoder`); when they match, the copy is deleted and the video model's is read where it is; when they do not, nothing changes and `phase` becomes `failed: ...`. `phase` is `idle` when done. `409` when the copy takes no space of its own (a clone) or no video model holds the same one. Also `409` while a `text_encoder.removing` left by an earlier switch is there and does not match that switch's record (the app deletes or restores only what the record accounts for). For a model already reading a video model's (or in `needs_choice`), `video_model` (a registered video model's folder) chooses which (`400` if it is not registered or has no text encoder); its files are read through in the background before it is recorded (`phase` is `reading the text encoder`; at once for files read before); one with different contents gives different images for the same seed. `409` during a setup or while an image is generated in any window. No image can be generated while the comparison or the reading runs. Returns the list. |
| `GET` | `/api/refmods` | The RefMod library (Model Manager > RefMod): each file's `id`, `name`, `path`, and from its header `format_version`, `bundle`, `file_name` and `members` (`index`, `kind` image/video/audio, `mode` full/compressed, `latent_t`/`latent_h`/`latent_w`, `tokens`, `name`, `source`, `pool`, `optimize_steps`, `supported`) - `null` while the file is still being read, with `error` when it cannot be. |
| `POST` | `/api/refmods/extract` | `{"path", "name"?, "mode"?, "resolution_cap"?, "latent_frames"?, "max_seconds"?}` makes a Full RefMod from an image, video or audio file into the RefMods folder: `mode` may only be `full` (`compressed` answers `400`: H3cApp no longer makes compressed RefMods, though it still loads them), `resolution_cap` the short-edge cap in pixels (default 1024), `latent_frames` the frames a video keeps (default 16), `max_seconds` the audio kept (default 15). `"paths": [...]` in place of `"path"` stacks 2 to 32 still images into one RefMod, one latent frame each in order (upstream's "stack"; `resolution_cap` defaults to 512 there; the first image sets the canvas and the others are cover-cropped to it). Answers `202` with `{"output"}`, the file it will write; `409` while another is being made. It runs on the engine's queue after any generation; `GET /api/status` reports `refmod_extracting` with `refmod_extract_phase`, `refmod_extract_progress` (the phase's own 0-1) and `refmod_extract_name`, and `message` says when it is done. |
| `POST` | `/api/refmods/extract/cancel` | Stops the RefMod being made (`409` if none is). |
| `GET` | `/api/loras` | Registered LoRA files (id, name, path, strength, recommended steps, whether enabled, step rule `sampler` and `audio_shift` as set in the model manager, and `recommended_sampling` from the file's metadata - `null` while the file is still being read). |
| `GET` | `/api/upscalers` | The enlargement methods: `id`, `label`, `available`, `min_scale` and `max_scale` (the range `scale` takes; a given video may stop earlier), and `reason` when one can't be chosen (not on this Mac, or its model not installed); `busy_reason` while a generation, cache build or import keeps it waiting. For `swiftVR` also `model_directory`, `model_installed` (the original weights are here), `original_removed` (they were deleted after conversion), `cache` (the converted `.h3vc` it runs from, or null), `license_accepted`, `setup` (`idle`, `listing`, `downloading`, `verifying`, `converting n/30`, `failed: …`, `done`), and the pinned source: `revision` (the H-oliday/SwiftVR revision the download is fixed to, the last whose model card declared the weights under the Apache License 2.0), `declared_license`, `verified` (the files here were checked by SHA-256 against that revision) and `verified_at`. The download (about 20 GB) and the conversion are started in the app (動画を拡大 → モデルを準備…, or モデル管理 → 拡大モデル) or with `POST /api/upscalers/swiftVR/setup`. |
| `POST` | `/api/upscalers/swiftVR/setup` | `{"confirm_license": true}` starts the same chain as the sheet's button: lists the pinned revision, downloads what is missing, checks every file's SHA-256 against that revision (a file that differs is deleted and named in `setup`), saves the license text and the record beside the weights, and converts for this Mac. Returns `{"ok", "setup"}`; `400` without the confirmation (it stands for having read the license notice the app shows), `409` while it is already running or, before the first conversion, while a generation, cache build or import holds the GPU. Follow `setup` in `GET /api/upscalers`. |
| `POST` | `/api/upscalers/swiftVR/remove-original` | Deletes the downloaded original weights (about 20 GB) once they are converted. The converted cache stays and SwiftVR keeps working. Returns `{"ok", "freed_bytes", "cache"}`; 409 when the original weights are not here, not converted for this Mac yet, or the model is being set up. Converting again needs a new download. |
| `POST` | `/api/upscalers/seedVR2/setup` | `{"confirm_license": true}` lists the pinned revision of mlx-community/SeedVR2-3B-mlx-int8, downloads what is missing (about 4.7 GB, resumable), checks every file's SHA-256 against that revision (a file that differs is deleted and named in `setup`) and saves the Apache License 2.0 text and the record beside the weights. No conversion: the engine reads the files. Returns `{"ok", "setup"}`; `400` without the confirmation, `409` while it is already running. For `seedVR2` and `seedVR2Video`, `GET /api/upscalers` reports `model_directory`, `model_installed`, `license_accepted`, `setup`, `revision`, `declared_license`, `verified` and `verified_at`; `seedVR2Video` also `window_frames` (17), `overlap_frames` (5) and `blend` (`hann`), how it cuts the video. |
| `POST` | `/api/upscalers/openH3/setup` | `{"confirm_license": true}` lists the pinned revision of Efficient-Large-Model/Open-H3-Regenerate-2K, downloads what is missing (the merged FP32 LoRA, about 12.5 GB, the latent upscaler, 691 MB, the license files; resumable; plus LightX2V Turbo v1.2, 1.4 GB, when the LoRA folder has no copy of the recorded revision), checks every file's SHA-256 against that revision (a file that differs is deleted and named in `setup`), extracts the refiner part alone (ranks 0–383) from the merged LoRA as BF16 (`extracting`, about 4.2 GB), deletes the merged file and writes the record. Returns `{"ok", "setup"}`; `400` without the confirmation, `409` while it is already running. For `openH3`, `GET /api/upscalers` reports `model_directory`, `model_installed`, `license_accepted`, `setup` (including `extracting`), `revision`, `declared_license` (MiniMax H3 Community License), `verified`, `verified_at`, `turbo` (the Turbo file it uses) and `max_pixels`. In `GET /api/upscalers`, `openH3` also lists the strengths it takes as `strengths` (`id`, `label`, `sigmas`) and `default_strength`. |
| `GET` | `/api/project` | The open project: name, path, `untitled` (a window's untitled project, kept in Application Support/H3cApp/UntitledProjects until saved; one from version 0.9 or earlier stays in Untitled), count, and its videos (file, seed, completion time, generation time, `continued_from`, `can_continue`, and for a joined video `joined_clips` / `planned_clips`; `source_image` is the `asset_id` of the project image a video's first frame is). Still images are under `images` (file, path, `asset_id`, `width`, `height`, completion time, `imported_from` for one brought in from a file, `has_latent`, and for a generated one `seed`, `prompt` and generation time; one made by an edit also has `references`, the pictures it was made from in order: `file`, `source_image` (the `asset_id` of the project image that picture is), the `width` and `height` it was encoded at and `used_latent`), with `importing_images` and `displayed_image` (the one in the preview). |
| `POST` | `/api/project/new` | `{"name", "directory"?}` creates a project from the current form (default directory `~/Movies/H3cApp`) and opens it. |
| `POST` | `/api/project/open` | `{"path"}` opens a project folder; the form takes its saved state. |
| `POST` | `/api/project/close` | Closes it. A window goes on with a new untitled project (`{"ok": true, "untitled": true}`); an untitled project with no video or image in it is deleted. |
| `POST` | `/api/project/save` | `{"name", "directory"?}` names the open untitled project: its folder, with every video, record and latent in it, moves to `directory/name` (default directory `~/Movies/H3cApp`) and the project takes the name. Waits for the move and returns the project; `400` for a project that already has a name or a folder that exists, `409` while a generation, enlargement, import, export or another move runs. |
| `POST` | `/api/project/move-video` | `{"video", "project"}` moves that video to the project folder `project`: its record and latent go with it, and for a joined generation its clips folder (`chains/<name>`); the input files the records use are copied into that project's `references`, and names already taken there get `-2`, `-3`… Waits for the move and returns `{"ok", "project", "video"}` (the name it has there); `400` with the reason (not a project, the same project), `409` while files are being written. |
| `POST` | `/api/project/restore` | `{"video"}` puts that video's request into the form with its seed fixed. |
| `POST` | `/api/project/use-as-reference` | `{"video"}` adds that video to the form as a reference video. |
| `POST` | `/api/project/delete-video` | `{"video"}` moves the video and its record to the Trash. |
| `POST` | `/api/project/join` | `{"video"}` joins the chain of continuations ending at that video into `<name>_joined.mp4` in the project, with a record, (cross-fading each carried-over stretch) and returns `{"path", "clips"}` when done. |
| `POST` | `/api/project/upscale-video` | `{"video", "upscaler"?, "scale"?, "strength"?}` makes an enlarged copy of that project video (`<name>_x2.mp4` at 2x, sound and metadata as they are); `scale` is a number with up to two decimals (default 2). It starts at 1 for the AI upscalers (the same size, redrawn) and at 1.1 for `standard` and `metalFX`, and stops at 8 for those two and at 4 for the others, and earlier for a video that reaches 4096 pixels a side, the GPU's memory or Open-H3's 1344x768: past that, a `400` naming the range. `upscaler` is `standard` (default: the same high-quality resize as the ×2 sizes), `metalFX` (MetalFX spatial scaling), `realESRGANGeneral` or `realESRGANAnime` (Real-ESRGAN AI upscaling, bundled), `swiftVR` (SwiftVR one-step AI video super-resolution; only when its weights are installed and converted, see plans/UPSCALE_PLAN.md), or `swiftVRFourX` (the same model restoring at 4x, in overlapping tiles when the frame is large, and the frames shrunk to the chosen scale: gentler and truer to the source, about five times the time). `seedVR2` is SeedVR2-3B frame by frame (the most detailed and by far the slowest; only when its weights are installed; experimental); `seedVR2Video` is the same model on windows of 17 frames with 5 cross-faded frames shared between windows (less flicker, about twice the time, up to 1920×1088 on a 24 GB Mac; experimental). `openH3` is the Open-H3 regeneration: the video's latents widened and redrawn by H3 itself in two or three steps; `strength` picks how much is redrawn, `light` (default, σ 0.4), `medium` (σ 0.7) or `strong` (σ 0.909, the source's recipe), and answers `400` for any other upscaler; the size is rounded into H3's 1344×768 limit, only generated videos with their latent file qualify, only while `GET /api/upscalers` reports `model_installed`, and a video or factor it can't do answers `400` with the reason (experimental). Answers at once with `{"video"}`, the name it will have; `400` if a side would pass 4096 pixels, `409` while another is being enlarged, or for `swiftVR`, `seedVR2` and `seedVR2Video` while a generation, cache build or import runs (they need the GPU to themselves). `GET /api/status` (and `GET /api/project`) report `upscaling_video`, `upscale_progress` (0-1) and `message`. |
| `POST` | `/api/upscale-file` | `{"path", "output", "upscaler"?, "scale"?}` writes any video file enlarged to `output` (an `.mp4` path), with the same upscalers and scales. The video is written to a hidden file next to `output` and replaces it only when complete, so an existing `output` stays as it was if enlarging fails or is cancelled; `output` naming the input itself (also through `..`, a symbolic link or a hard link) is `400`. `403` when a web page on another site sends it (a foreign `Origin`, or `Sec-Fetch-Site: cross-site` / `same-site`); scripts and `curl` are unaffected. `409` as above. Answers at once; progress and the result as above. |
| `POST` | `/api/upscale/cancel` | Stops the enlargement running now; its unfinished file is removed. `409` if none is running. |
| `POST` | `/api/project/import-video` | `{"path", "size_profile"?, "carry_frames"?, "crop_position"?}` brings a video made elsewhere into the open project to continue it: converted to the size closest to its own (`"size_profile": "current"` keeps the form's, a size name uses that) and 24 fps, with the form set to continue it; `carry_frames` (22, 39 or 56; default 22) is how much of its end is carried over; `crop_position` (`[x, y]`, 0-1 each; default `[0.5, 0.5]`) is where the kept part sits across what a different aspect ratio cuts off (`[0, 0.5]` keeps the left). Answers at once with `{"video"}`, the name it will have; once converted it is listed by `GET /api/project` and usable as `continue_from`. |
| `POST` | `/api/kind` | `{"kind": "video" \| "image"}` switches what the composer makes. Each side keeps its own prompt and settings. |
| `POST` | `/api/project/import-image` | `{"path"}` or `{"paths": [...]}` brings image files into the open project as still images (`images/` in the project folder; an untitled project is started when none is open). A PNG is kept as it is; any other format is converted to PNG, upright, with the metadata it carried. Each gets a record naming the file it came from, and is not marked as AI-generated. Answers at once with `{"ok", "count"}`; the images are listed by `GET /api/project` once in (`importing_images` while it runs, `message` if a file could not be read). |
| `POST` | `/api/project/show-image` | `{"image"}` shows that image (a file name under `images` from `GET /api/project`) in the preview. |
| `POST` | `/api/project/use-image` | `{"image", "as"}` hands that image to the video form without generating: `"as": "first_frame"` starts a video from it (the image's prompt goes into an empty video prompt), `"last_frame"` ends on it, `"reference"` adds it as a reference image (the answer carries a `warning` when the active model has no Ref2VA). The composer switches to videos; the image is copied into the project's `references` like any other input, with its record. For an image edit instead: `"edit"` makes the image the image form's only reference, at the image's own size (an empty image prompt gets `Edit <Picture 1>. ` to start from), and `"edit_reference"` adds it to the image form's references; the composer switches to images. |
| `POST` | `/api/project/delete-image` | `{"image"}` moves the image, its record and its latent to the Trash. |
| `POST` | `/api/project/upscale-image` | `{"image", "method"?, "factor"?, "strength"?}` Enlarge: makes a larger copy of that image as a new project image. `method` is `redraw` (the default: the image model in use draws it again; it runs as an image generation, seen in `GET /api/status`'s `generating_image` and progress preview) or `standard`, `metalFX`, `realESRGANGeneral`, `realESRGANAnime`, `swiftVR`, `swiftVRFourX`, `seedVR2` (run as an enlargement, seen in `GET /api/project`'s `upscaling_video` and `upscale_progress`; `POST /api/upscale/cancel` stops it). `factor` is 1 to 8 (default 2; a redraw goes up to about 8 megapixels, the others to 4096 pixels a side); `strength` is a redraw's `gentle`, `standard` (default) or `strong`. `202` once started; `400` or `409` with the reason when it cannot start. | `POST` | `/api/project/move-image` | `{"image", "project"}` moves that image to the project folder `project` with its record and latent (a name already taken there gets `-2`, `-3`…). `POST /api/generate` body fields, all optional except `prompt`:

| Field | Default | Notes |
|---|---|---|
| `prompt` | — | Required. |
| `size_profile` | `"square"` | A preset `<shape>-<size>` with shape `square`, `landscape` or `portrait` and size `small`, `medium` or `large`, plus `-x2` for the 2x upscaled output (e.g. `landscape-large-x2`: 960x544 upscaled to 1920x1088); or `custom-<W>x<H>` / `custom-<W>x<H>-x2` for a finished size of W x H (multiples of 32, or of 64 with `-x2`, which generates at half that size); the generated size must be at most 600,000 pixels with 256-1344 per side. The older names `smallSquare`, `square`, `landscapeNative`, `landscapeUpscaled`, `portraitNative` and `portraitUpscaled` still work and stand for the matching small/medium presets (see `SizeProfile` in [GenerationModels.swift](../native/H3Spike/Sources/H3cApp/GenerationModels.swift)). |
| `seconds` | `5` | 1–15. |
| `steps` | `20`, or the first enabled Turbo LoRA's recommended steps; `6` with a HyperFlow H3 Flash model | 2–40; 4, 6 or 8 when the active model is HyperFlow H3 Flash ([GGUF](GGUF.md#hyperflow-h3-flash)), which also answers `400` with the reason for LoRAs, a speed preset other than `quality`, `reuse` other than 1, `dit_layers` other than 50, `sampler: "renoise"` and an `audio_shift` other than 3. |
| `reuse` | `2` | 1–3. The faster speed modes run at 1 whatever this is. |
| `compute_mode` | the app's own default for this GPU | `attentionCache`, `resident`, or `ssdStreaming`. |
| `speed_mode` | `"quality"` | `quality`, `fast`, or `fastest` (see [Speed modes](TECHNICAL.md#speed-modes)). |
| `dit_layers` | `50` | 35–50. Fewer blocks can break the audio. |
| `fast_attention` | `false` | `true` for [fast mode](TECHNICAL.md#fast-mode-experimental); `400` where it isn't available. |
| `seed` | random | 0–18446744073709551615, as a number or a decimal string (a string keeps a large seed exact for clients whose JSON numbers are doubles). |
| `first_frame_path` / `last_frame_path` | none | FL2VA anchors; cannot combine with `reference_paths`. |

| `forced_audio_path` / `forced_audio_offset` | none / `0` | Lip sync: this file's audio (an audio file or a video's soundtrack), from `forced_audio_offset` seconds on, is held as the soundtrack while the picture is generated to match it, and the output carries that audio itself. | `reference_paths` | `[]` | Ordered Ref2VA references; image/video/audio is auto-detected per path, and a `.safetensors` path is a RefMod (a saved reference latent, see `GET /api/refmods`). An entry may also be an object `{"path", "strength"?, "member"?}` for a RefMod: `strength` above 0 and at most 1 (default 1), `member` the 0-based member of a bundle (required for a bundle; `-1`, the default, for a single-latent file). At least one image, video or RefMod is required if any audio path is included. |
| `loras` | `[]` | The LoRA stack for this job: names from `GET /api/loras`, or `{"name": ..., "strength": 0.8}` objects (strength multiplies the adapter's trained scale; omitted keeps the entry's saved strength). ### From other devices

The API listens on `127.0.0.1` only unless **全体設定 >
同じネットワークのほかの機器からAPIを使えるようにする** is on. Then it also
answers on the Mac's network addresses - the settings list them, such as
`http://192.168.1.5:8420` and `http://<name>.local:8420` - so another Mac or
a phone on the same network can use it, with the same token. While this is
on the token is kept across launches (another device cannot read the token
file); turning it off replaces it, so a token handed to another device stops
working. macOS may ask once whether H3cApp may accept incoming connections.

The traffic is plain HTTP, not encrypted: any device on the same network
can read the token, prompts and videos as they pass. Use it only on a
network you trust, such as your home's; elsewhere, reach the Mac through an
SSH tunnel instead (`ssh -L 8420:127.0.0.1:8420 <user>@<mac>.local`, with
Remote Login on), which keeps the API on `127.0.0.1`. Paths in requests are
paths on the Mac running H3cApp. A connection may take at most 30 seconds
to send its request, a request body at most 1 MB, and 32 connections are
served at once.
