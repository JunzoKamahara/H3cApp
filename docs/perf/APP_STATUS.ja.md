## 所見

**31件すべてが成功した**（生成30件と、途中での中止1件）。各動画のまんなかのコマを並べて目で確かめ、壊れた映像は無かった。どれも1回ずつの値で、電源はACである。始める前から、システムのスワップを4.5 GiB使っていた（前の作業の残り）。

### 生成時間

512×512・5秒・20ステップ（アプリの標準）では、次のとおり。

| 設定 | 生成時間 |
|---|---|
| int8キャッシュ（計算方式を指定しないときの方式） | 7分07秒 |
| SSD streaming | 10分14秒 |
| 常駐 | 14分35秒 |
| 速度モード：高速 | 4分39秒 |
| 速度モード：最速 | 3分26秒 |
| 高速モード（CCV） | 7分01秒 |

- **常駐は、このMac（24GB）ではint8キャッシュの2倍かかった。** ピークが20.2 GiBになり、生成の間にスワップが4.5→6.4 GiBに増えた。常駐とint8キャッシュのlatentは全バイト一致したので、出力は同じで、遅くなるだけである。計画は23.2 GiB（搭載メモリの97%）と見積もっている。
- 高速モード（CCV）は、この大きさではint8キャッシュと差が無かった（7分01秒と7分07秒）。CCVの呼び出しは550回で、経路は使われている。
- サイズと長さ：256×256が1分30秒、672×384と384×672が約6分50秒、960×544が17分48秒、512×512の10秒が18分14秒。
- 3秒の動画（基準3分41秒）：reuse 1が6分06秒、reuse 3が2分52秒、DiT 40層が3分06秒、Turbo LoRAの4ステップが1分57秒、DMAD LoRAの8ステップが3分16秒、HyperFlowの6ステップが2分54秒。
- 動画VAEの復号と書き出しは、512×512の3秒で約40秒、5秒で約70秒、10秒で2分15秒、960×544の5秒で1分52秒かかる（256×256の5秒は12秒）。ステップ数を減らした設定ほど、全体に占める割合が大きい（Turbo LoRAでは1分57秒のうち46秒）。

### M1〜M4相当の構成（TensorOps無し）での確認（11月21日）

- 5秒以上の512×512、大きいサイズ、LoRA、速度モード、HyperFlow。

- **時間：** 既定の方式どうし（M5はint8キャッシュ、M4 MaxはSSD streaming）では、M4 Maxが1.01〜1.17倍だった。SSD streamingどうしの標準設定では、M4 Maxのほうが速かった（0.78倍）。M3 Proは、どの設定でもM4 Maxの2.59〜3.11倍で、標準設定の5秒が23分51秒、960×544・5秒と512×512・10秒が約54分だった。
- **常駐：** M4 Maxでは、SSD streamingより速くならなかった（8分08秒と7分57秒）。ピークは39.77 GiB（デノイズ。DiTの読み込みで38.19 GiB）で、計画は43.9 GiBと見積もった。M3 Pro（18GB）では、計画の43.9 GiBが搭載メモリを超えるので、生成の前に断った（意図どおり）。
- **動画VAEの時間：** 動画VAEの段階は、512×512・3秒でM5が40.1秒、M4 Maxが32.7秒、M3 Proが87.5秒、標準設定のSSD streaming（5秒）で72.8秒、56.6秒、151.9秒だった。M4 MaxはF32の重みでも、M5のint8より速い。上の節の模擬（M5でTensorOpsを切ると約3.2倍）は、M5のGPUでの値で、M4 Maxにはあてはまらなかった。
- **メモリ：** 動画VAEの段階は、M4 Maxが10.32〜12.08 GiB、M3 Proが10.11〜12.01 GiBで、どの設定でもプロセス全体のピークだった（M4 Maxの常駐を除く）。起動して最初の1本では、動画VAEに入る直前の使用量が0.38 GiB（M3 Pro）と0.49 GiB（M4 Max）で、ピークは10.25 GiBと10.32 GiBだった。2本目からは直前の使用量が0.96〜3.29 GiBで、ピークも上がった。上の「メモリ」の節の、生成を重ねると解放済みの領域が残る現象と同じと考えているが、2台では確かめていない。v0.11.0の計画は、ここを12.0 GiB（動画デコーダ）と見積もる。起動して最初の1本は1.7 GiBの余裕を残して収まり、生成を重ねた後の最大12.08 GiB（M4 Max、つなげて生成）は、これを0.08 GiB上回った。v0.10.2の計画は動画デコーダを数えておらず、5.5〜8.7 GiBと見積もっていた。
- **スワップ：** M3 Proでは、0.8 GiBから最大3.1 GiBに増えたが、生成は止まらなかった。M4 Maxでは、常駐の生成の前が9.2 GiB、後が26.5 GiBで、その後はそのままだった。128GBのMacでピーク39.77 GiBなら、ふつうはここまで増えない。同じ時間にほかのアプリがメモリを使っていたかは、記録から分からない。
- **出力：** 同じMacの中では、latentが全バイト一致した。3秒の基準、SSD streamingの3秒、2倍に拡大、2本続けての1本目、途中の様子を表示、中止の後の生成が、M4 Maxで`3a2d500632e9627c`、M3 Proで`379e21415fb6a5b8`である。M4 Maxでは、常駐とSSD streamingの標準設定も一致した（`a4b02729b8f86248`）。Macどうしでは、同じ設定でも一致しなかった（同じ経路を通るM3 ProとM4 Maxの間でも）。GPUの世代で計算の順序や丸めが違うためと考えているが、確かめていない。
- **使えなかったもの：** int8キャッシュと高速モード（CCV）は、どちらのMacでも使えなかった。int8キャッシュはTensorOps（`MTLGPUFamilyApple10`）、CCVはNeural Accelerator（`ccv_attention_supported`）が条件で、どちらも意図どおりである。LoRAとHyperFlowは、どちらのMacにも登録されていなかったので試していない。
- **M3 Proのログ：** 「Failed to import MPS module」が92回出た（macOS 27.2.1。M4 MaxとこのM5では出ていない）。アプリとエンジンのコードが出すものではない。生成はすべて成功した。
- 中止は、どちらもデノイズに入って約16秒で止まり、次の生成は普通に通った。

確かめていないこと：

- **映像。** 記録とログだけを受け取り、動画ファイルは見ていない。
- **v0.11.0以降の版。** 2台ではv0.10.2だけを動かした。

### メモリ

- **起動して間もないうちは、ピークは約5.0〜5.4 GiBで、動画VAEの段階にある**（int8キャッシュ、SSD streaming、速度モード、中までのサイズ）。計画の表示は5.2 GiBである。
- **常駐は20.2 GiB、HyperFlow（常駐で動く）は15.8 GiB**で、DiTの重みを全部載せるぶん大きい。計画はそれぞれ23.2 GiB、18.9 GiBと見積もる。
- **アプリを起動したまま生成を重ねると、生成していないときのメモリが増えた。** 起動直後は0.08 GiB、1本つくると0.84〜0.95 GiB、960×544をつくった後は2.11 GiB、その後は2.33〜2.39 GiBのまま続いた。途中で調べると、解放済みの大きい領域をmacOSのmallocが抱えている分が2.1 GiBあった（`vmmap`の「Malloc Large (empty)」。中身は圧縮またはスワップに出ている）。12.6節で直したテキストエンコーダの一時バッファと同じ現象で、復号したフレームなど別の領域で起きている。
- その分だけ、後の生成のピークも上がった。同じ512×512・3秒でも、動画VAEの段階が6.4〜7.0 GiB、テキストエンコーダの段階が7.2〜7.5 GiBになった（起動して間もないときは約5.2 GiBと約4.9 GiB）。
- 増え続けるわけではない。つなげて生成の後には0.83 GiBに戻り、その後は1.0〜1.4 GiBだった。
- **計画の見積もりは、この分を数えていない。** 見積もりは新しく起動したプロセスの値で、生成を重ねた後の実測は、見積もりを最大で約2 GiB上回った（動画VAE：計画5.2に対し7.0、テキストエンコーダ：計画5.4に対し7.5）。24GBのMacでは判定は変わらないが、16GBのMacではその分の余裕が減る。

### 機能

- 入力の種類（最初の画像、最初と最後の画像、参照画像、RefMod、音声に合わせる、続きを作る）は、どれも動いた。RefModは、参照画像から作るところ（3.5秒）から確かめた。
- つなげて生成（256×256・16秒、5秒ずつ）は、つないだ1本（396コマ、16.5秒）ができた。2本続けて生成は2本でき、2本目のseedは乱数になった。
- 2倍に拡大は、512×512を1024×1024にした動画ができた。
- 途中の様子は、デノイズの間に画像を取得できた。
- 中止は、デノイズに入って16秒で止まり、動画は残らず、次の生成は普通に通った。
- HyperFlowは、reuseが1のときだけ受け付ける。2を指定すると、APIが理由を付けて断った（最初の指定の誤りで、1にしてやり直して成功した。やり直しは、アプリを起動し直した直後の1本である）。
- 同じプロンプトで続けたので、入力が同じ生成ではテキストエンコーダを省いた（条件のキャッシュ）。入力を変えた設定では走り、約6.6秒だった。

### 確かめていないこと

- 画面の操作と表示。すべてAPIから動かした。
- 15秒の動画、768×768、960×544の10秒以上。時間がかかるので入れていない。
- AIを使う拡大（SwiftVR、SeedVR2、Open-H3）、静止画（静止画は別に確かめた。`DIFFUSERS_FFN_SPLIT.ja.md` 14節）、int8キャッシュの作成、モデルの取り込み。
- LoRAの重ねがけ、参照に動画や音声を使う生成、カスタムクリップ。
- 署名したアプリと、インストール済みのアプリの設定を引き継いだ起動。切り離したコピーで動かした。
- M1・M2の実機、16GB・8GBのMac（TensorOps無しの構成は、このM5で模擬した。M3 Pro（18GB）とM4 Max（128GB）の実機は、v0.10.2で確かめた。上の節）。
- 同じ設定の繰り返し。時間は1回ずつの値で、温度やほかの負荷で変わる。

### 次に手を入れる候補

1. 復号したフレームなど、大きい一時領域もシステムへ返す（12.6節と同じ方法）。生成していないときの2.3 GiBが約0.9 GiBに、生成を重ねた後のピークが約1.5 GiB下がる見込みがある。効果は未測定。
2. 計画の見積もりを、アプリのプロセスでの実測に合わせて見直す。1を先に行えば、差は小さくなる。
3. 常駐を、24GBのMacでも選べるままにするかを決める。このMacではint8キャッシュより遅く、スワップを使う。
