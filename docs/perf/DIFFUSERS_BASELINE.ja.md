# Diffusers取り込み計画 P0：基準測定とバッファ寿命

測定日：2026年11月17日  
対象：`DIFFUSERS_H3_ADOPTION_PLAN.ja.md` のP0と、その結果から追加したP0b（8.2節、4.1節）  
ブランチ：`diffusers-p0`（`52372a9`に計測用の変更とP0bの変更を加えたもの）

3〜7節の数値は、P0bを入れる前（`activated`が専用のバッファを持つ状態）の測定である。P0bを入れた後は、int8経路の活性領域が158.4から116.4 KiB／トークンになる。P0bより前の状態は`H3_DISABLE_DIT_ACTIVATED_IN_QKV=1`で再現できる。

## 1. 結論

1. **このMac（M5・24GB）のアプリ設定では、DiTのメモリは制約になっていない。** DiT段階のピークは「固定分＋158.3 KiB×トークン数」で、960×544・15秒（55,785トークン）でも10.4〜10.9GiBだった。先に限界になるのは時間である。この条件の20ステップは約2.9時間かかり、その87%がAttentionである（5節）。
2. **活性領域は全部が実メモリである。** GPUが一部でも書いたバッファは全ページが常駐する。int8経路の`qkv`は3分の1しか使われていないが、全体がメモリを消費している（7節）。
3. **分割なしで活性領域を26%減らした（P0b、既定で有効）。** `activated`を`qkv`バッファと共用し、`qkv`をその大きさに縮めると、158.4から116.4 KiB／トークンになる。出力は、動画の17構成と静止画モデルの4構成でフレーム（画像）・latentともビット一致した（8.2節。うち2構成は共用の対象外で、従来どおり動くことの確認）。計画書のP1（FFN分割）の机上見積もり（35 KiB／トークン）より大きく、カーネルの変更もない。
4. **SDPAの実行方式（full／chunked）でメモリは変わらず、時間の差も6%以内である。** 「方式の切り替えでメモリを減らす」案は効果がない（6節）。
5. **メモリ計画（`h3_plan.c`）はint8経路で2〜4GiB過大に見積もっていた。** BF16経路の係数（199.5 KiB／トークン、固定4GiB）を全モードに使っていたためである（4節）。P0bで、int8経路の係数を126 KiB／トークンにし、LoRAのファイルの大きさを数えるようにした（4.1節）。
6. **テキストエンコーダはT2Vでは約6秒で、全体の1%未満である。** ClipProj（P3）の時間面の利点はT2Vにはない。一方、512×512・5秒ではテキストエンコーダ（4.75GiB）がプロセス全体のピークである。
7. **時間の測定はAC電源で行う必要がある。** このMacはバッテリー駆動時に低電力モードが有効になる設定で、DiTが約1.7倍遅くなる（5節）。

### 4.1 メモリ計画の係数（P0bで変更）

`h3_plan.c`のDiT段階の見積もりは「固定4.0GiB＋1トークンあたりの係数＋テキスト行1つあたり64 KiB＋常駐する重み」である。変更は2点。

- **int8経路の係数を126 KiB／トークンにした。** 対象は、テンソル演算ユニットのあるGPU（M5）で、SSD streamingでもHyperFlowでもない場合（`h3_plan_input.dit_int8`）。内訳は、5,376幅のBF16が4本（`hidden`、`mod_attention`、`attention_output`、token reductionの退避分）、7,168幅が3本、14,336幅が1本、int8の14,336幅が1本。実測は116.4 KiB／トークン（token reductionなし）。それ以外の経路と、静止画の計画（`h3_image.c`。int8 ConvRotをそのまま流す経路も共用の対象だが、計画は変えていない）は従来の199.5 KiB／トークンのまま。
- **LoRAのファイルの大きさの1.3倍を加えた。** ブロックを流す方式では、LoRAの係数がデノイズの間GPUに残る。1.29GiBのLoRAで、DiT段階のピークが1.61GiB増えた（4,547トークン・4ステップで2.97→4.58GiB）。これまでは数えておらず、BF16の係数の余裕に隠れていた。

固定分の4.0GiBは変えていない。実測の固定分は2.45GiB（2ステップ）〜2.78GiB（20ステップ）で、差の約1.2GiBが余裕になる。core reuseは5,376幅のバッファを2本追加する（実測で137.5 KiB／トークン）が、係数には入れていない。約6万トークンまでは固定分の余裕に収まる。

## 5. 時間

AC電源（低電力モードなし）での値。Aは20ステップの実行、B・Cは2ステップの実行。

| | A | B | C |
|---|---|---|---|
| テキストエンコーダ | 6.2秒 | 6.2秒 | 6.2秒 |
| デノイズ1ステップ（full方式） | 28.2秒 | 94〜96秒 | 528〜531秒 |
| うちAttention（推定） | 15.7秒（56%） | 68秒（71%） | 461秒（87%） |
| うちAttention以外（推定） | 12.5秒 | 27秒 | 68秒 |
| 映像VAEデコード | 62秒 | 107秒 | 301秒 |
| 20ステップのデノイズ | 565秒（実測） | 約32分（換算） | 約2.9時間（換算） |

- Aの20ステップは全体で635秒。内訳はデノイズ89%、映像VAEデコード10%、テキストエンコーダ1%。ステップごとの時間は28.0〜28.8秒で安定していた。
- Attentionの時間は系列長の約2乗（A→Bで1.9乗、B→Cで2.0乗）、それ以外は約1乗で増える。長い系列ほどAttentionが支配的になる。
- 「Attention」と「それ以外」の分け方は推定である。full方式のSDPAはプロファイルのGPU時間（`root-gpu`）に含まれず、chunked方式では含まれることから、full方式での「壁時計時間 − `root-gpu`」をAttentionの時間とした。
- 24GBの85%に達する約11.7万トークンでは、この増え方から1ステップ30分以上になる。このMacでは、DiTのメモリより先に時間が実用の限界になる。

**電源の影響：** このMacは「バッテリー駆動時は低電力モード」の設定になっている（`pmset -g custom`）。バッテリー駆動ではAの1ステップが47.3秒（AC電源の1.68倍）、Cが約1,000秒（1.89倍）だった。メモリの値は電源で変わらない。時間を比べる測定はAC電源で行い、実行の前後で電源を記録する（`tools/perf/p0_run.sh`がJSONとログに書く）。今回の測定のうち、09:08〜10:30の実行（`b768_s2_chunked`、`c960_s2_full`、`a512_s2_base`／`share1`／`share2`、`b768_s2_share2`、`a512_s20_full`）はバッテリー駆動で、`b768_s2_full`は途中で電源が変わった。これらの時間は使わない。AC電源で取り直した実行は名前の末尾が`_ac`である。

## 6. SDPAの実行方式

M5での既定はfull（MPSGraphの1回呼び出し）。`H3_SDPA_MODE=chunked`と比べた。AC電源、各1回、2ステップ。

| | full（1／2ステップ目） | chunked（1／2ステップ目） | DiTピーク full／chunked |
|---|---|---|---|
| A | 30.6／31.9秒 | 33.2／32.9秒 | 3.94／3.94GiB |
| B | 95.9／94.3秒 | 91.3／92.8秒 | 5.73／5.75GiB |
| C | 531.0／527.7秒 | 513.6／496.9秒 | 10.90／10.44GiB |

- メモリの差はない（Cの0.3〜0.5GiBの差は、同じfull方式の2回の実行が10.73と10.90GiBだったのと同程度）。int8経路ではQ・K・Vが最初からhead-majorで作られるため、chunked方式にscratchが要らず、full方式も内部でスコア行列を実体化していない。
- 時間の差は6%以内で、Aではfull、B・Cではchunkedがわずかに速い。各1回の測定なので優劣は確定できない。
- 計画書のP0項目9・10にあった「長系列でのSDPA方式の自動選択」は、メモリの削減策としては効果がない。

## 7. 確保量と常駐量

**GPUが一部でも書き込んだバッファは、全ページが常駐する。** 単体のプローブ（1GiBのBF16バッファを確保し、GPUのコピーで先頭4分の1だけ書く）の結果：

| 時点 | プロセスのフットプリント | 1GiBバッファの常駐量 |
|---|---|---|
| 確保した直後 | 変化なし | 0 |
| GPUが先頭4分の1に書いた後 | +1.03GiB | 1.00GiB |
| GPUが末尾4分の1にも書いた後 | 変化なし | 1.00GiB |

確保しただけのバッファはメモリを消費しないが、GPUの演算に束縛された時点で、書き込まれない部分も含めて全体が実メモリになる。計画書2.3節で保留にしていた点の答えは「見かけの確保ではなく実メモリ」である。

`H3_DIT_ARENA_TRACE=1`は、DiTの解放時に活性領域ごとの確保量と常駐量を表示する。3ケースとも全領域で確保量と常駐量が一致した。

## 8. 分割を伴わない削減

### 8.1 活性領域の寿命表

`allocate_activations()`（`src/model/h3_dit_setup.c`）が確保し、`run_block()`（`src/model/h3_dit_block.c`）が使う領域。幅は1トークンあたりの要素数、KiBは1トークンあたりのバイト数（BF16は2バイト、int8は1バイト）。「区間」は下の手順番号で、その領域の内容が生きている範囲を示す。

通常H3・int8経路（M5）の1ブロックの手順：

1. （ブロック0とtoken reductionの境界だけ）AdaLN：`hidden` → `mod_attention`
2. QKV射影＋正規化＋RoPE：`int8_activation`（5,376幅。量子化前なら`mod_attention`から量子化）→ `query`、`key`、`value`
3. SDPA：`query`、`key`、`value` → `attention_heads`
4. Attention出力射影：`attention_heads` → `int8_activation`（7,168幅）→ `attention_output`
5. attention gate＋MLP AdaLN＋量子化：`hidden`、`attention_output` → `hidden`（in-place）、`int8_activation`（5,376幅）
6. MLP：`int8_activation`（5,376幅）→ FC1+SwiGLU → `activated` → 量子化 → `int8_activation`（14,336幅）→ FC2 → `mlp_output`
7. MLP gate＋次ブロックのAdaLN＋量子化：`hidden`、`mlp_output` → `hidden`（in-place）、`int8_activation`（5,376幅。次ブロックの手順2が読む）

| 領域 | dtype | 幅 | KiB／トークン | 生きている区間（int8経路） | 別名・共用 | 他の経路での使い方 |
|---|---|---|---|---|---|---|
| `hidden` | BF16 | 5,376 | 10.5 | 常時 | なし | 同じ |
| `mod_attention` | BF16 | 5,376 | 10.5 | 1→2（ブロック0と境界だけ） | なし | BF16・非融合・ConvRot・HyperFlowでは毎ブロック1→2 |
| `query`、`key`、`value` | BF16 | 7,168×3 | 42.0 | 2→3 | なし | 同じ |
| `qkv` | BF16 | 21,504（P0b以降、int8経路では14,336） | 42.0（同28.0） | 先頭7,168幅を3→4（`attention_heads`として） | `attention_heads`、`mod_mlp`が同じバッファ | BF16のQKV射影は全幅を2で使う。HyperFlowは生のQ（7,168幅）とFC1のゲート半分（14,336幅）を置く。token reductionは後方に元の`hidden`を退避する |
| `attention_output` | BF16 | 5,376 | 10.5 | 4→5、6→7（`mlp_output`として） | `mlp_output`が同じバッファ | 同じ |
| `activated` | BF16 | 14,336 | 28.0 | 6の中だけ | P0b以降、int8経路では`qkv`と同じバッファ（8.2節） | HyperFlowは生のK（7,168幅）を2に置く |
| `int8_activation` | int8 | 14,336 | 14.0（128行単位に切り上げ） | 2、4、5→6、6、7→次の2で内容が入れ替わる | 4つの用途で共用 | int8経路だけ |
| `int8_activation_scales` | F32 | 14 | 0.06 | 同上 | 同上 | 同上 |
| `fc1` | BF16 | 28,672 | 56.0 | 6の中だけ | なし | BF16の非融合MLPだけ（int8経路では確保しない） |
| `lowrank_tmp` | BF16 | 最大ランク | — | — | なし | HyperFlowだけ |
| `core_input`、`core_residual` | BF16 | 5,376×2 | 21.0 | ステップをまたぐ | なし | core reuseが2以上のときだけ |

活性領域はすべて生成の最初に確保され、生成の終わりまで解放されない。したがって「寿命」が意味を持つのは、区間が重ならない領域どうしを同じメモリに置けるかどうかの判断である。int8経路では次の組が重ならない。

- `attention_heads`（3→4）と`activated`（6）。`activated`の14,336幅は`qkv`の21,504幅に収まる。
- `query`・`key`・`value`（2→3）と`activated`（6）。
- `mod_attention`（1→2）と`attention_output`（4→7）。

### 8.2 `activated`を`qkv`と共用する（P0b、既定で有効）

int8のMLPの活性（`activated`、14,336幅）を、専用のバッファではなく`qkv`バッファに置く。実装は`allocate_activations()`（`src/model/h3_dit_setup.c`）にある。カーネル、形状、束縛offsetは変えていない。

- **共用できる理由：** FC1が`activated`を書く時点で、`qkv`バッファにあるほかの内容はもう使われない。`attention_heads`はAttention出力射影が読み終えている。MLPの入力（`mod_mlp`。入力量子化を融合しない経路でだけ`qkv`に置かれる）は、FC1より前の別のパスで`int8_activation`へ量子化される。
- **`qkv`の大きさ：** QKV射影もint8なら、射影は`query`・`key`・`value`へ直接書くので、`qkv`を21,504幅から14,336幅へ縮める。token reductionは元の`hidden`を`qkv`の後方（縮小時の使用分の後ろ）に退避する。収まらないときは`qkv`をその分だけ大きくする。
- **対象外（従来どおり専用のバッファを確保）：** BF16のMLP（M1〜M4、SSD streaming。`mod_mlp`を読みながら`activated`を書く）、HyperFlow（生のQを`qkv`に、生のKを`activated`に同時に置く）、活性領域の別名を無効にした診断構成、BF16の重みを残す診断構成。
- **無効化：** `H3_DISABLE_DIT_ACTIVATED_IN_QKV=1`で専用のバッファに戻る。

| | 共用なし | 共用あり（既定） |
|---|---|---|
| 活性領域（KiB／トークン） | 158.4 | 116.4 |
| A・2ステップのDiTピーク | 3.94GiB | 3.56GiB |
| B・2ステップのDiTピーク | 5.74GiB | 4.87GiB |
| C・2ステップのDiTピーク | 10.90GiB | 8.67GiB |
| A・20ステップのDiTピーク | 4.27GiB | 3.88GiB |
| core reuse 2のとき（KiB／トークン） | 179.5 | 137.5 |

出力の比較。共用あり（既定）と共用なし（`H3_DISABLE_DIT_ACTIVATED_IN_QKV=1`）で同じ生成を実行し、エンコード前のRGBフレームの全バイトと、保存したlatentファイルを比べた（`tools/perf/p0_pair.sh`）。特記のないものは512×512・49フレーム（4,547トークン）・2ステップ、int8キャッシュ、通常H3。

| 構成 | 結果 |

## 9. GPU APIの行範囲対応（計画書P0の項目5）

- int8のMLP・線形・量子化・QKVのカーネルは、すべてバッファをoffset 0で束縛する（`h3_gpu_linear.m`に56か所、`h3_gpu_blocks.m`に239か所）。行範囲を指定する引数はない。
- 行範囲を扱う前例は3つある。BF16のTensorOps線形（`h3_gpu_linear.m`、2,048行を超え3,072行以下のとき行範囲に分けて束縛offsetで処理）、chunked方式のSDPA（`h3_gpu_attention.m`、`MPSNDArray`のバイトoffset）、`_offset`付きのAdaLN・パッチ射影・コピー。
- 別名テンソル（`h3_gpu_tensor_alias_*`）はページ境界のoffsetが必要で、重なる別名どうしの順序が保証されない。同じテンソルを別の名前で使う共用（`attention_heads`と`qkv`、今回の`activated`と`qkv`）にはこの制約がない。

## 10. 再現手順

```bash
make h3_generate_cli
```

```bash
tools/perf/p0_run.sh a512_s2_full 512 512 124 2
```

P0bより前の確保で測るとき：

```bash
tools/perf/p0_run.sh a512_s2_base 512 512 124 2 H3_DISABLE_DIT_ACTIVATED_IN_QKV=1
```

ある設定の有無で出力がビット一致するかを調べるとき（2回実行して、フレームとlatentを比べる。6番目の引数が2回目だけに付く設定）：

```bash
tools/perf/p0_pair.sh v_token 512 512 49 2 H3_DISABLE_DIT_ACTIVATED_IN_QKV=1 H3SPIKE_TOKEN_REDUCTION=1
```

単独の実行でフレームとlatentを残すときは、`H3SPIKE_DUMP=<ファイル>`と`H3SPIKE_SAVE_LATENT=<ファイル>`を引数に加える。メモリが尽きる前にプロセスを止めるため、スクリプトは`H3_MEMORY_LIMIT_GIB=22`を設定する。
